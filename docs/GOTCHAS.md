## <a name="1"></a>1. `brew` and `--version` disagree

**Symptom.** `brew upgrade kind` says `Warning: kind 0.33.0 already installed`, but
`kind --version` says `0.25.0`.

**Cause.** `PATH` is finding a different binary than the one brew manages.

**Fix.** Never trust the package manager; ask the binary, then find out which one runs:

```bash
which -a kind          # -a lists EVERY match, not just the first
ls -l /usr/local/bin/kind
```

→ SETUP Step 1.1

## <a name="2"></a>2. Docker client installed, daemon not running

**Symptom.** `docker --version` works; `kind get clusters` emits a long error ending
`Cannot connect to the Docker daemon ... Is the docker daemon running?`

**Cause.** Having the client is not having the daemon.

**Fix.** `docker info` returns empty `CPUs=0 Mem=0` when it is down. Start Docker Desktop and
**wait**: `until docker info >/dev/null 2>&1; do sleep 5; done`

→ SETUP Step 0.2

## <a name="3"></a>3. macOS cannot reach the container network at all

**Symptom.** `curl https://172.18.0.6:6443/version` → `000`. `netstat -rn | grep 172.18` → nothing.

**Cause.** Not a bug. Docker Desktop runs containers in a Linux VM and macOS has no route to it.

**Critically: no in-cluster load balancer can fix this.** kube-vip, MetalLB and Cilium LB IPAM all
allocate an equally unreachable address. The blocker is the host↔VM boundary.

**Fix.** Docker Desktop 4.26+ `kernelForUDP` ("kernel networking for UDP") plus a host route.

→ SETUP Steps 2.3b and 3.5

## <a name="4"></a>4. The host bridge is not called `bridge101`

**Symptom.** Guides say `bridge101`; `ifconfig bridge101` → `does not exist`.

**Cause.** macOS assigns the number. This machine got **`bridge100`**.

**Fix.** Find it by its `vmenet` member, never by number:

```bash
ifconfig -l | tr ' ' '\n' | grep -E '^bridge'
ifconfig bridge100 | grep -E 'inet |member'
```

→ SETUP Step 3.5.2

## <a name="5"></a>5. `sudo` cannot prompt from a non-interactive shell

**Symptom.**
`sudo: a terminal is required to read the password; either use the -S option ... or configure an askpass helper`

**Cause.** No TTY. Applies to CI, scripts, and Claude Code's `!` prefix.

**Fix.** Run it in a real Terminal window. Or avoid sudo entirely with the proxy-container
approach in SETUP Step 3.5b.

## <a name="6"></a>6. A Docker restart destroys a multi-node kind cluster

**The most expensive mistake in this build.**

**Symptom.** After restarting Docker, all containers come back `Up` — and the cluster is dead.
`kubectl` hangs, then:

```
kube-apiserver ... Exited (attempt 5)
E run.go:72] "command failed" err="error creating storage factory: context deadline exceeded"
W grpc: addrConn.createTransport failed to connect to {Addr: "127.0.0.1:2379" ...}
```

**Cause.** Docker reassigns container IPs on start, in whatever order they come up:

| Container | Before | After |
|---|---|---|
| `poc1-control-plane` | 172.18.0.3 | **172.18.0.7** |
| `poc1-control-plane2` | 172.18.0.4 | **172.18.0.2** |

etcd's peer URLs and the API server's certificate SANs were written around the *original*
addresses. etcd cannot form a quorum; the API server cannot reach its datastore.

**Fix.** There is no recovery — `kind delete cluster` and rebuild. **Prevention is the point:**
make **every** Docker Desktop change (memory, `kernelForUDP`) **before** creating any cluster, in
**one** restart.

→ SETUP **Step 2.7**, a hard gate before Step 3

## <a name="7"></a>7. Cilium can't reach an API server that is demonstrably up

**Symptom.** All agents `Pending`; the `config` init container loops:

```
level=info msg="Establishing connection to apiserver" ipAddr=https://172.18.0.7:6443
```

But from a node, `curl -sk https://172.18.0.7:6443/version` returns **200 in 9ms**.

**Cause.** TLS, not connectivity. The API server certificate's SANs list
`DNS:poc1-external-load-balancer` but **not** the load balancer's IP:

```
DNS:...,DNS:poc1-external-load-balancer
IP Address:10.11.0.1, IP Address:172.18.0.4, IP Address:127.0.0.1
```

Cilium verifies the certificate; `curl -k` does not.

**Fix.** Pass the **DNS name**, never the IP:
`--set k8sServiceHost=poc1-external-load-balancer`

**The transferable lesson:** when something cannot reach an API server that is demonstrably up,
**check the certificate SANs before the network.** `curl -sk` succeeding while the real client
fails is the signature of a TLS-verification problem — `-k` disables exactly the check the client
performs.

*Bonus:* the name is also stable. Across three rebuilds the load balancer's IP was `.7`, `.6`,
`.2`; the name never changed.

→ SETUP Step 5.3

## <a name="8"></a>8. kind's load balancer is Envoy, not HAProxy

**Symptom.** Guides say HAProxy; `docker ps` shows `envoyproxy/envoy:v1.36.2`.

**Fix.** Cosmetic, but check rather than assume — it changes where you look for logs.

## <a name="9"></a>9. Every node is `NotReady` after creating the cluster

**Symptom.** All nodes `NotReady`, all pods `Pending`.

**Cause.** **Expected.** `disableDefaultCNI: true` means there is no CNI until you install one.

**Fix.** Do not debug it. Install Cilium; all nodes go `Ready` within seconds.

## <a name="10"></a>10. `cilium status` reports errors right after a restart

**Symptom.** `Envoy DaemonSet: 1 errors`, `Hubble Relay: 1 errors` immediately after
`rollout restart`.

**Cause.** Pods are still rescheduling.

**Fix.** Re-run it. On this build a run showing errors was fully green a minute later with no
intervention.

## <a name="11"></a>11. Hubble CLI warns about a version mismatch

**Symptom.** Every `hubble` command prints
`Hubble CLI version is lower than Hubble Relay ... cli=1.19.4 relay=1.20.1`.

**Cause.** Cilium 1.20.1 ships Relay 1.20.1, but the `cilium/hubble` CLI repo's newest release
**is** 1.19.4. There is no matching CLI to install.

**Fix.** None needed. Filter it: `| grep -v level=WARN`.

## <a name="12"></a>12. `kubectl patch` silently reverted by the next `helm upgrade`

**Symptom.** `hubble-ui` was patched to `type: LoadBalancer`, worked, then silently returned to
`ClusterIP` when an unrelated `helm upgrade --reuse-values` ran.

**Cause.** Helm owns that Service. An imperative patch is not in the release, so the next
reconciliation reverts it.

**Fix.** Set it as a **value** (`hubble.ui.service.type`), never with `kubectl patch`.

## <a name="13"></a>13. A LoadBalancer IP moved and broke a bookmark

**Symptom.** Hubble UI stopped answering on `172.18.255.200`; that address now served the Gateway
and returned `403`.

**Cause.** LB IPAM allocates the **next free** address, so an address depends on **creation
order**. hubble-ui lost `.200` during a helm upgrade and came back on `.201`, while the Gateway
took `.200`.

**Fix.** Pin it, so the address is a property of the service rather than of startup order:

```yaml
annotations:
  "io.cilium/lb-ipam-ips": "172.18.255.201"
```

## <a name="14"></a>14. The two LB CRDs are on different API versions

**Symptom.**
`Warning: cilium.io/v2alpha1 CiliumLoadBalancerIPPool is deprecated; use cilium.io/v2`
— but changing *both* resources to `v2` fails.

**Cause.** They did not graduate together. In Cilium 1.20.1:

| Resource | Version |
|---|---|
| `CiliumLoadBalancerIPPool` | `cilium.io/v2` |
| `CiliumL2AnnouncementPolicy` | `cilium.io/v2alpha1` **only** |

**Fix.** One manifest, two `apiVersion` values. Check, never assume:
`kubectl api-resources | grep -iE 'loadbalancerippool|l2announcement'`

## <a name="15"></a>15. The Gateway gets 503 — policy applies to it too

**Symptom.**
`upstream connect error or disconnect/reset before headers. reset reason: connection timeout [503]`

**Diagnose it right:** a 503 **from Envoy** means the Gateway is healthy and the *backend hop*
failed. Hubble names the culprit:

```
10.10.3.168:60206 (ingress) <> deathstar:80 Policy denied DROPPED (TCP Flags: SYN)
```

**Cause.** `ingress` is Cilium's reserved identity for its Gateway proxy. An existing policy
admitted only `org=empire`. **A Gateway is not a privileged bypass.**

**Fix.** Allow the `ingress` entity explicitly — then read #16 before you do.

## <a name="16"></a>16. A policy fix silently created a security hole

**The most important entry here, because it looks like success.**

**Symptom.** After allowing the `ingress` entity on TCP 80, the Gateway worked — and so did this:

```bash
curl -XPUT http://172.18.255.200/v1/exhaust-port
```
```
Panic: deathstar exploded
```

The L7 policy protecting that path was still applied, and still protecting pod-to-pod traffic.

**Cause.** **Cilium policies are additive.** A broader L3/L4 allow for a *new* source does not
inherit the narrower L7 restriction written for a *different* source — it grants that source the
whole port.

**Fix.** Restate every restriction that matters for the new client:

```yaml
      toPorts:
        - ports: [{port: "80", protocol: TCP}]
          rules:
            http:
              - method: "POST"
                path: "/v1/request-landing"
```

**The rule: an allow-list union is only as strict as its most permissive member.**

## <a name="17"></a>17. Performance features enable in config but stay inactive

**Symptom.** `--set bandwidthManager.enabled=true` applies cleanly, the ConfigMap says `true`, the
agent logs `--enable-bandwidth-manager='true'` — and status says `BandwidthManager: Disabled`.

**Cause.** The kernel lacks the facility, and Cilium disables the feature:

```
level=warn msg="BPF bandwidth manager could not read procfs. Disabling the feature."
  error="could not open the sysctl file /host/proc/sys/net/core/default_qdisc"
```

This linuxkit kernel has **seven** entries in `/proc/sys/net/core/`. BBR is not even compiled in —
`tcp_available_congestion_control` reports only `reno cubic`. netkit needs ≥6.7; this is 6.6.12.

**Fix.** None on this kernel — but **verify, do not assume**. Reading
`--enable-bandwidth-manager='true'` in the log is **not** the same as reading
`BandwidthManager: Enabled` in the status. Check both, plus the kernel facility.

## <a name="18"></a>18. Benchmarking straight after a rollout measures the rollout

**Symptom.** 7659 Mbits/sec and 9705 Mbits/sec in the same pair of runs.

**Cause.** Measured immediately after `rollout restart`, while agents were still reprogramming.

**Fix.** Settle ~45s. And take ≥5 samples: this rig has a **25% spread** across identical runs, so
any claimed difference smaller than that is noise.

## <a name="19"></a>19. One Cilium module is permanently `Degraded`

**Symptom.** `Modules Health: Stopped(0) Degraded(1) OK(94)`.

**Cause.** Find it rather than worrying:

```bash
cilium-dbg status --all-health | grep -A2 socket-termination
```
```
[DEGRADED] service LV socket termination not supported by kernel
```

Another linuxkit limitation.

**Fix.** None needed. 94/95 modules OK; no impact on any demo. Know this before quoting
`Degraded(1)` as a fault.

## <a name="20"></a>20. ClusterMesh refuses to connect: CA mismatch

**Symptom.**
```
Error: Cilium CA certificates do not match between clusters poc1 and poc2.
Use --allow-mismatching-ca to allow this by adding remote CAs to the CA bundle
```

**Cause.** Each cluster generated its own Cilium CA at install.

**Fix — and resist the flag.** `--allow-mismatching-ca` adds each cluster's CA to the other's
bundle, so a mesh of N clusters trusts N independent roots instead of one. Share the CA instead:

```bash
kubectl --context kind-poc1 -n kube-system get secret cilium-ca -o yaml \
  | grep -v '^\s*\(resourceVersion\|uid\|creationTimestamp\|selfLink\)' \
  | kubectl --context kind-poc2 -n kube-system apply -f -
```

**Better: pass the same `tls.ca.cert`/`tls.ca.key` at install time** and it never arises. Copying
afterwards only works while the second cluster has issued nothing that matters.

## <a name="21"></a>21. Deleted certs are regenerated by a quarterly CronJob

**Symptom.** After deleting the old CA's certs, `clustermesh-apiserver` will not start:

```
Warning FailedMount  MountVolume.SetUp failed for volume "etcd-server-secrets" :
        secret "clustermesh-apiserver-server-cert" not found
```

Restarting pods does not help. **Neither does `helm upgrade`.**

**Cause.** In the chart values:

```
clustermesh.apiserver.tls.auto: {method: 'cronJob', schedule: '0 0 1 */4 *'}
```

A CronJob, **quarterly**. Delete the secrets and nothing regenerates them until the 1st of the
month, four months out.

**Fix.** Trigger it by hand:

```bash
kubectl -n kube-system create job clustermesh-certgen-manual \
  --from=cronjob/clustermesh-apiserver-generate-certs
```

Completes in ~4s. Confirm the new cert carries the shared CA by comparing `openssl x509 -dates`
against the other cluster's — they must be identical.

## <a name="22"></a>22. Benchmarks fail in the `default` namespace

**Symptom.** A benchmark pod cannot reach its server; traffic is dropped.

**Cause.** The `default` namespace carries demo 02's default-deny policy. You are measuring policy
denial, not throughput.

**Fix.** Put benchmarks in their own namespace, and pin the pods to **different nodes** with
`nodeName` — otherwise the scheduler may co-locate them and you measure a loopback `memcpy`.

*Related:* the `networkstatic/iperf3` image has no `wget` or `curl`; use `kubectl exec` into a pod
that has one.

## <a name="23"></a>23. A kubectl context outlives its cluster

**Symptom.** `kubectx` lists a context whose cluster no longer exists:

```
kind-kind-cluster      <- stale
kind-poc1
kind-poc2
```

`kind get clusters` reports only `poc1` and `poc2`. Using the stale context gives a connection
error that reads like a broken cluster rather than a missing one.

**Cause.** `kind delete cluster` removes its context, but a cluster deleted another way — or a
kubeconfig copied between machines — leaves the entry behind.

**Fix.** Cross-check `kubectx` against `kind get clusters`, and prune:

```bash
kubectl config delete-context kind-kind-cluster
```

## <a name="24"></a>24. A benchmark conclusion that did not survive a re-run

**Symptom.** Session A produced intra-cluster 8714 Mbit/s (spread 25%) and cross-cluster 8098
(spread 2%), which reads as "cross-cluster costs ~7% and is unusually consistent". Session B, same
rig and commands an hour later, produced intra 6626 (spread 37.7%) and cross 7845 (spread 26.4%) —
**cross-cluster now faster by 18%, and its 2% consistency gone.**

**Cause.** The difference between the two configurations was smaller than the variation within
each. On a laptop where both clusters share a kernel, a bridge and a CPU with everything else
running, whichever path is least contended at that moment wins.

**Fix.** Never publish a comparison whose difference is smaller than the spread of its own
samples. `scripts/bench.sh` prints the spread next to the median precisely so this is visible
before a conclusion is written. If the difference does not exceed the spread, the honest result is
*"this rig cannot measure it"*.

**Why it is in this list:** the wrong conclusion was written into a README first and only caught by
re-running. Measuring once and moving on is how it gets published.

## <a name="25"></a>25. A full Docker disk looks like a TLS/etcd bug

**The most misleading failure in this build.**

**Symptom.** Immediately after switching ClusterMesh to cert-manager certificates, both clusters'
`clustermesh-apiserver` pods began crash-looping. `etcd-init` hung at `"Configuring root user"`
and exited 255 after its 2-minute timeout.

**Three wrong hypotheses, in order:** pod contention (two replicas fighting), a live mesh
interfering with a cert change, and an etcd init timeout too short for a loaded disk. All plausible
given what had just changed. All wrong.

**The actual cause** was in the `etcd` container's log — a container nobody had looked at, because
the suspicion was on the thing just modified:

```
{"level":"error","msg":"writing data failed: write /var/run/etcd/member/snap/db: no space left on device"}
{"level":"fatal","msg":"failed to commit tx","error":"... no space left on device"}
```

```bash
docker run --rm --privileged --pid=host alpine nsenter -t 1 -m -u -n -i df -h /var/lib
```

```
/dev/vda1   58.4G  55.4G  0  100%  /var/lib
```

**Zero bytes free on the Docker VM disk.** Nothing to do with certificates.

**Where the space goes.** Every kind node's writable layer, every image and every volume share one
pool inside the VM. `docker system df` showed 104 images totalling 28.9 GB with 27 GB reclaimable.

**Fix:**

```bash
docker builder prune -af
docker image prune -af      # reclaimed 24.63 GB here
```

Both apiservers then reached `3/3 Running` with **zero restarts in 40 seconds**.

**Related: where does etcd data live in kind?** Not on your Mac directly. Each node is a container
on the VM disk, and `clustermesh-apiserver`'s etcd uses an **`emptyDir`** — a directory inside that
container. So mesh etcd, cluster etcd, images and volumes all compete for the same 58 G. The
`emptyDir` also means mesh etcd is deliberately **ephemeral**: a cache rebuildable from the
Kubernetes API, not a database of record, which is why restarts are safe.

**The lesson:** a component failing right after you changed X is not evidence that X caused it.
**Read the failing container's own logs before theorising about what you just touched** — one `df`
would have replaced three hypotheses.

## <a name="26"></a>26. A GitHub release is not a Helm chart release

**Symptom.**
`Error: INSTALLATION FAILED: chart "cert-manager" matching v1.21.2 not found in jetstack index`

**Cause.** cert-manager v1.21.2 was tagged on GitHub that morning; the Helm repo index still had
v1.21.1. The two publish independently.

**Fix.** Take the version from the chart repo, not a releases page:

```bash
helm search repo jetstack/cert-manager --versions | head -3
```

## <a name="27"></a>27. GNU `sed` range syntax that BSD/macOS `sed` rejects

**Symptom.**
`sed: 1: "/annotations:/,/^  [a-z ...": extra characters at the end of d command`

**Cause.** A range address with multiple patterns and an embedded `d` — a GNU extension. macOS
ships BSD sed.

**Fix.** For stripping fields out of Kubernetes objects, rebuild the object instead of editing its
text. It is portable and states exactly which fields survive:

```bash
kubectl get secret X -o json | python3 -c 'import json,sys; s=json.load(sys.stdin); print(json.dumps({...}))'
```

## The meta-lesson

Most of these share a shape: **something reported success while not working.**

- brew said "already installed" (#1)
- Docker containers all came back `Up` (#6)
- the API server answered `curl -k` with 200 (#7)
- `kubectl patch` succeeded (#12)
- the Gateway policy fix "worked" (#16)
- `--enable-bandwidth-manager='true'` appeared in the log (#17)
- `clustermesh connect` printed `✅ Connected` (#20 — before status was checked)

**Verify the thing you actually care about, with a tool that would notice if it were false.** That
is why this repo's READMEs quote captured output, why `scripts/verify.sh` exists, and why the
failures above are kept rather than tidied away.
