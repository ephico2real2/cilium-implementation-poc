# Demo 08 — An enterprise CA for ClusterMesh, with cert-manager

## Summary context

**The problem with how demo 07 established trust.** It copied Cilium's own self-signed
`cilium-ca` Secret from poc1 to poc2. That works, and it is what Cilium's docs show for a quick
start, but it is not how an enterprise runs PKI:

- the CA is generated by the CNI as a side effect of installation, not issued by an authority;
- it is distributed by `kubectl get secret | kubectl create -f -`, a manual copy with no record;
- nothing renews the leaf certificates on a schedule you control;
- adding a third cluster means remembering to copy the Secret again.

**The enterprise pattern.** One root CA is the trust anchor. Every cluster runs cert-manager and
issues its *own* leaf certificates from that shared root. Certificates renew automatically.
Joining a new cluster means provisioning the trust anchor, not copying working certificates.

**Cilium's actual requirement**, from the ClusterMesh docs:

> *"Every cluster must trust the certificates presented by the other clusters. Use a common root
> CA, or configure `tls.caBundle` with every trusted CA certificate."*

A shared root satisfies that with **one** anchor. Per-cluster intermediates also work in
principle, but then each cluster needs the full chain — and getting that wrong is
[cilium/cilium#43099](https://github.com/cilium/cilium/issues/43099), *"x509: certificate signed
by unknown authority"*, which affected v1.18.4–v1.19.0 and was fixed in #43230. We run 1.20.1 so
the fix is present; a shared root avoids the class of problem entirely.

**This demo assumes the CA lives in poc1.** In a real environment it would more likely live in a
dedicated PKI cluster or an HSM-backed offline root, and only the *issuer* would live in each
workload cluster. The mechanics below are unchanged by that.

---

## ⚠ Order matters: trust BEFORE join

**In an enterprise the mesh does not exist yet when you set the CA up.** The trust anchor is a
*prerequisite* of joining, not something retrofitted afterwards.

This build learned that the hard way by doing it backwards — changing the certificate authority
underneath a live, connected mesh. The correct sequence is:

```
1. install cert-manager in every cluster
2. create the root CA (here: in poc1)
3. distribute the root to every other cluster
4. create the SAME ClusterIssuer name in every cluster
5. point Cilium at that issuer            <- certificates are now issued from the shared root
6. THEN enable and connect the mesh
```

If you already have a mesh, **disconnect it first** (`cilium clustermesh disconnect`), do steps
1–5, then reconnect.

## Part 1 — cert-manager in both clusters

Both clusters need the **controller and CRDs**, not just the CA material: each cluster issues its
own leaf certificates locally.

```bash
helm repo add jetstack https://charts.jetstack.io && helm repo update jetstack
```

```bash
for ctx in kind-poc1 kind-poc2; do
  helm install cert-manager jetstack/cert-manager --version v1.21.1 \
    --namespace cert-manager --create-namespace --kube-context "$ctx" \
    --set crds.enabled=true
done
```

```bash
for c in kind-poc1 kind-poc2; do
  echo "$c: $(kubectl --context $c get crd | grep -c cert-manager.io) CRDs"
done
```

```
kind-poc1: 6 CRDs
kind-poc2: 6 CRDs
```

> **Gotcha — a GitHub release is not a Helm chart release.** cert-manager **v1.21.2** was tagged on
> GitHub the morning this was written, and installing it failed:
> `chart "cert-manager" matching v1.21.2 not found in jetstack index`. The chart repo only had
> v1.21.1. Check with `helm search repo jetstack/cert-manager --versions` rather than reading a
> version off a GitHub releases page.

## Part 2 — the root CA, in poc1

`01-root-ca-poc1.yaml` creates three objects, and the layering is the point:

| Object | Purpose |
|---|---|
| `Issuer/selfsigned-bootstrap` | can only sign self-signed certs. Exists **solely** to sign the root below — a root is self-signed by definition, and cert-manager needs some issuer to do it |
| `Certificate/clustermesh-root-ca` | the actual root. `isCA: true`. Its private key lands in a Secret — **the crown jewels**: whoever holds it can mint a certificate the whole mesh trusts |
| `ClusterIssuer/ca-issuer` | what Cilium points at. `ClusterIssuer`, not `Issuer`, because it must be usable from `kube-system` |

```bash
kubectl --context kind-poc1 apply -f demos/08-certmanager-ca/01-root-ca-poc1.yaml
```

```bash
kubectl --context kind-poc1 -n cert-manager get certificate clustermesh-root-ca
kubectl --context kind-poc1 get clusterissuer ca-issuer
```

```
NAME                  READY   SECRET                AGE
clustermesh-root-ca   True    clustermesh-root-ca   12s

NAME        READY   AGE
ca-issuer   True    12s
```

```
subject=CN=clustermesh-root-ca
issuer=CN=clustermesh-root-ca        <- self-signed: it IS the root
notBefore=Sep 11 15:02:41 2026 GMT
notAfter=Sep  8 15:02:41 2036 GMT    <- 10 years; leaves rotate far more often
```

## Part 3 — distribute the root to poc2

Only the **CA Secret** crosses the boundary. poc2 then issues its own certificates locally.

```bash
kubectl --context kind-poc1 -n cert-manager get secret clustermesh-root-ca -o json \
  | python3 -c '
import json, sys
s = json.load(sys.stdin)
print(json.dumps({
  "apiVersion": "v1", "kind": "Secret", "type": s.get("type", "kubernetes.io/tls"),
  "metadata": {"name": s["metadata"]["name"], "namespace": "cert-manager"},
  "data": s["data"]}))' \
  | kubectl --context kind-poc2 apply -f -
```

> **Why a script and not `sed`.** The obvious `kubectl get -o yaml | sed -e /resourceVersion/d ...`
> pipeline used a GNU-sed range-with-multiple-patterns form that **BSD sed on macOS rejects**:
> `sed: 1: "/annotations:/,/^  [a-z ...": extra characters at the end of d command`. Rebuilding the
> object in Python is portable and states exactly which fields survive.

Then the **same issuer name** in poc2, backed by the copied root:

```bash
kubectl --context kind-poc2 apply -f demos/08-certmanager-ca/02-issuer-poc2.yaml
```

**Verify both clusters trust the same root** — compare fingerprints, do not assume:

```bash
for c in kind-poc1 kind-poc2; do
  kubectl --context $c -n cert-manager get secret clustermesh-root-ca \
    -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -fingerprint -sha256
done
```

```
kind-poc1  72:16:61:3E:82:57:59:05:B3:4A:67:0D:AC:ED:14:DC:E6:46:B4:B8:1E:7D:88:27:11:7F:64:8C:43:18:0C:D5
kind-poc2  72:16:61:3E:82:57:59:05:B3:4A:67:0D:AC:ED:14:DC:E6:46:B4:B8:1E:7D:88:27:11:7F:64:8C:43:18:0C:D5
```

**Identical.** One trust anchor, two clusters.

A useful intermediate observation: before the Secret was copied, poc2's `ca-issuer` sat at
`READY: False` — cert-manager correctly refusing to act as a CA whose key it does not have. The
dependency is visible in the status rather than hidden.

## Part 4 — point Cilium at the issuer

Applied identically to **both** clusters, which is why the issuer name had to match:

```bash
for ctx in kind-poc1 kind-poc2; do
  helm upgrade cilium cilium/cilium --version 1.20.1 -n kube-system --kube-context "$ctx" --reuse-values \
    --set clustermesh.apiserver.tls.auto.enabled=true \
    --set clustermesh.apiserver.tls.auto.method=certmanager \
    --set clustermesh.apiserver.tls.auto.certManagerIssuerRef.group=cert-manager.io \
    --set clustermesh.apiserver.tls.auto.certManagerIssuerRef.kind=ClusterIssuer \
    --set clustermesh.apiserver.tls.auto.certManagerIssuerRef.name=ca-issuer
done
```

Cilium now creates cert-manager `Certificate` resources instead of running a CronJob:

```bash
kubectl --context kind-poc1 -n kube-system get certificate
```

```
NAME                                READY   SECRET                              AGE
clustermesh-apiserver-admin-cert    True    clustermesh-apiserver-admin-cert    29s
clustermesh-apiserver-local-cert    True    clustermesh-apiserver-local-cert    29s
clustermesh-apiserver-remote-cert   True    clustermesh-apiserver-remote-cert   29s
clustermesh-apiserver-server-cert   True    clustermesh-apiserver-server-cert   29s
```

Four per cluster, eight in total, all `READY` — and **cert-manager renews them automatically**,
which the quarterly CronJob of demo 07 did not do on any schedule you controlled.

## Part 5 — verify the chain, then join

```bash
for c in kind-poc1 kind-poc2; do
  kubectl --context $c -n kube-system get secret clustermesh-apiserver-server-cert \
    -o jsonpath='{.data.tls\.crt}' | base64 -d | openssl x509 -noout -issuer
done
```

```
kind-poc1  issuer=CN=clustermesh-root-ca
kind-poc2  issuer=CN=clustermesh-root-ca
```

**Both clusters' mesh certificates are now issued by the enterprise root.** Only now is it correct
to join:

```bash
cilium clustermesh connect --context kind-poc1 --destination-context kind-poc2
cilium clustermesh status --context kind-poc1 --wait
```

## ⚠ The failure that dominated this demo — and it was not TLS

While switching the mesh to cert-manager, both clusters' `clustermesh-apiserver` pods began
crash-looping. The obvious suspicion was the certificate change, and **three successive hypotheses
were wrong**: pod contention, a live mesh interfering, and an etcd init timeout. The actual error
was in the `etcd` container, not the init container or anything TLS:

```
{"level":"error","msg":"writing data failed: write /var/run/etcd/member/snap/db: no space left on device"}
{"level":"fatal","msg":"failed to commit tx","error":"write /var/run/etcd/member/snap/db: no space left on device"}
```

```bash
docker run --rm --privileged --pid=host alpine nsenter -t 1 -m -u -n -i df -h /var/lib
```

```
Filesystem   Size   Used  Available  Use%  Mounted on
/dev/vda1   58.4G  55.4G         0  100%  /var/lib
```

**The Docker VM's disk was 100% full with zero bytes free.**

### This answers "where does etcd data live in kind?"

It is **not** in the container image and **not** on your Mac's filesystem directly:

- each kind node is a container whose writable layer and volumes live in the **Docker VM's**
  `/var/lib` (`/dev/vda1` above, 58.4 G on this machine);
- `clustermesh-apiserver`'s etcd uses an **`emptyDir`** (`etcd-data-dir: {}`), which is a directory
  on the **node**, i.e. inside that container, i.e. on that same VM disk;
- so mesh etcd, cluster etcd, every image and every volume compete for one 58 G pool.

`emptyDir` also means the mesh etcd is **deliberately ephemeral** — it is a cache of state that can
be rebuilt from the Kubernetes API, not a database of record. That is why a pod restart is safe,
and why "the data is empty each time" is by design rather than a bug.

**Reclaiming it:**

```bash
docker builder prune -af
docker image prune -af
```

```
Total reclaimed space: 24.63GB
/dev/vda1   58.4G  23.0G  32.4G  41%  /var/lib
```

Both apiservers then went `3/3 Running` with **zero restarts in 40 seconds**.

**The lesson, and it is the recurring one in this repo:** a component failing right after you
changed X is not evidence that X caused it. The certificate change was innocent; three hypotheses
about it were wrong; the answer was in the *other* container's logs, and it took one `df` to
confirm. **Read the failing component's own logs before theorising about the thing you just
touched.**

## What to take away

| | demo 07 (quick start) | demo 08 (enterprise) |
|---|---|---|
| Trust anchor | Cilium's self-signed `cilium-ca` | a root CA you created and control |
| Distribution | copy working certs between clusters | distribute the **root**; each cluster issues its own |
| Renewal | quarterly CronJob | cert-manager, automatic |
| Adding a cluster | copy the Secret again | provision the root, apply the same issuer |
| Order | join, then fix trust | **trust first, then join** |
