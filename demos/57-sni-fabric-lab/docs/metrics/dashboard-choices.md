# Dashboard: what was chosen, and why

The dashboard (`observability/grafana/dashboards/fabric.json`, generated by
`observability/grafana/build_dashboard.py`; Perses form in `observability/perses/fabric.json`)
follows diagram-kit's dashboard standard. This page records the inventory, the questions, the
metric that answers each, and what was looked at and left out.

## Decisions the data forced

- **Envoy's 5xx counter counts only the final answer.** Measured after a chaos run:
  orders-api answered 93 status updates with 503 (its own `orders_api_http_requests_total`
  and `orders_api_chaos_injected_total` both read 93), Envoy made 92 retries of which 61
  succeeded, and `envoy_cluster_upstream_rq_xx` (class 5) read 2, the same as the 5xx callers
  saw on `mesh_http` and the 2 events the worker requeued. So a failed attempt that was
  retried is not in Envoy's 5xx count. The retry section therefore sets orders-api's own 5xx
  count (every attempt) beside Envoy's (what reached the caller); the gap is what retries
  absorbed. The first draft of that panel said Envoy's counter showed every failed attempt;
  that was wrong and was replaced.
- **Counter names without `_total`.** Prometheus 3.15 flags `rate()` over a counter whose
  name does not end in `_total` ("metric might not be a counter"). Seven are renamed at the
  scrape (`metric_relabel_configs` in `observability/prometheus.yml`): five of Envoy's and two
  of postgres-exporter's. The admin portal's queries use the new names.
- **MQ has no per-queue metrics here.** The IBM MQ container's exporter emits
  queue-manager-wide series only (`ibmmq_qmgr_*`, 88 names); there is no `ibmmq_queue_*`. The
  dashboard shows queue-manager puts and gets; the admin portal counts the messages waiting on
  `DEV.QUEUE.1` and the dead-letter queue with a REST browse, which removes nothing.
- **Counters created at zero.** The worker creates every `worker_messages_total{result}`
  series at start-up, so "dead-lettered" reads 0 rather than "No data" before the first one.

## Looked at and left out

| Metric | Why left out |
|---|---|
| `envoy_tcp_downstream_cx_rx_bytes_total` / `_tx_bytes_total` per tenant | Bytes add little to connections for these tenants; worth adding when a tenant carries bulk data |
| `envoy_cluster_upstream_rq_time_bucket` per cluster | orders-api's own buckets answer the latency question for the hop that matters; Envoy's adds a second view of the same request |
| `envoy_cluster_outlier_detection_ejections_*` | Single-host clusters: Envoy's panic threshold keeps routing to an ejected host, so ejections never change traffic here |
| `ibmmq_qmgr_failed_mqget_total` | The worker's REST gets wait up to 5 s on an empty queue; whether an empty wait counts as a failed get was not measured, so the panel could mislead |
| `ibmmq_qmgr_cpu_*` | Under amd64 emulation CPU figures describe the emulator more than MQ |
| `pg_stat_database_numbackends` | Connection count is steady (one pool); transactions answer "is it answering" better |
| `tcp_svc_active_connections` | Connections last milliseconds; the gauge is almost always 0 |
| process and runtime series (`process_*`, `python_*`, `go_*`) | They describe the processes, not the questions |
