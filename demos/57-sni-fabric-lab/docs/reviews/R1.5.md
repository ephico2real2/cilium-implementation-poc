# Review record: R1.5, the trace crosses IBM MQ

Issue #98. Two independent designs from one brief, by Codex (`gpt-5.6-sol`, `high`) and OB1-lite
(Opus 5.5, `high`), arbitrated by the orchestrator on 2026-10-23; built from OB1-lite's patch,

[the tracing page](../tracing.md#across-ibm-mq-one-order-one-trace).

## The two designs, and what was taken

Both designs agree on the structure: orders-api puts the event in a `send DEV.QUEUE.1` span
(kind producer) and sends that span's W3C `traceparent` as the MQ user property `ibm-mq-usr`; the
worker processes each message in a `process DEV.QUEUE.1` span (kind consumer) whose parent is that
context, which OpenTelemetry's messaging conventions allow ("MAY use the message's creation
context as its parent") and which AC 1 needs; every put of the worker's own is a `send` span the
next attempt continues; `messaging.system` is `ibm_mq`, for no registered value names IBM MQ;
`opentelemetry-api` is declared where the code imports it, the locks otherwise unchanged.

| Point | Codex | OB1-lite | Taken, and why |
|---|---|---|---|
| Reading `ibm-mq-usr` | one property per header instance, read with `get_list` (issue #98's guidance) | MQ returns every property in one header, sorted and comma-joined: split at commas outside quotes | OB1-lite's. Measured by the orchestrator on `DEV.QUEUE.3`: two properties put as two headers came back as `other;"a,b";string,traceparent;"…";string`, one header. #98's guidance is retracted; the spike carried one property and could not show it |
| `tracestate`, `baggage` | not carried: optional, may hold commas | not carried: MQ refuses a value with `;` (`MQWB0302E`, HTTP 400), which both may hold | not carried, for OB1-lite's reason, measured again by the orchestrator |
| Sweeper and republish | a new trace, no schema change | the order row stores its request's `traceparent` (`ADD COLUMN IF NOT EXISTS`); a re-send joins the order's trace, linking to the republish request | OB1-lite's: the story is "one order is one trace", and recovery is when a reader follows an order; the cost is one nullable column |
| The worker's empty polls | kept: 118 root traces in 10 minutes | suppressed with `suppress_http_instrumentation()`; failed gets stay in `worker_get_errors_total` and the log | OB1-lite's: they were every one of the worker's traces |
| Business attribute | `order.id` | `fabric.order.id` | OB1-lite's: a custom attribute takes a namespace, so a future registered name cannot clash |
| Forcing a requeue for AC 2 | chaos `fail_rate=1` with a delay, reset in time | chaos `fail_next`: the next n status updates fail; phase 6 sets 4, Envoy's first try and 3 retries | OB1-lite's: no timing race; phase 5's setting answers `fail_next` 0. `fail_next` is one budget for all status updates, so another update in that moment can take a forced failure; the check then fails (`first_ok=1`), never passes falsely, and a leftover costs one requeue (OB3, measured) |
| `MAXPROPL` in `30-fabric.mqsc` | set explicitly | unchanged | unchanged: QM1 already reports `MAXPROPL(NOLIMIT)` |
| Tests | Python unit tests, no lab | `tests/scripts/test_mq_trace_context.sh`: both services' code in their built images against fakes, 35 checks after the review; 26 false-pass cases | OB1-lite's, run in CI's container-tests job |

## Review: Codex (`gpt-5.6-sol`, `high`) and OB3 (Opus 5.5), head `198e4c4`

Both NOT MERGE-READY; OB3 on the documentation only, having confirmed the code, `verify.sh` and
the tests by runs (mutants of `mq_trace_summary` each caught; `fail_next 4` matching Envoy's 4
tries in its access log; 200,000 fuzzed headers, none raised). The orchestrator read the
conventions' text before deciding the convention findings.

| Finding | From | Decision |
|---|---|---|
| The `process` span has no link to its creation context; the conventions say every `process` span SHOULD link to it, and their example shows parent and link together | Codex, OB3 | applied: a link when the context is valid, none for a new root |
| A failed messaging span has no `error.type`, which the conventions make conditionally required on failure | Codex | applied on orders-api's and the worker's send spans and on a failed `process` span: the HTTP status or the exception's name |
| A non-numeric `attempt` raised out of the loop and stopped the worker (from before R1.5) | Codex, OB3 | applied: read inside the decode guard, so the event is dead-lettered as unreadable |
| A failed dead-letter put was still counted `dead_lettered` (from before R1.5) | Codex | applied: `dead_letter` counts `lost` when MQ refused the put |
| The worker's `receive` span is left out, which the conventions ask for on a pull | Codex | kept, and said on the tracing page: every empty poll was a trace |
| `fail_next` is one budget for every status update, and the check resets it without a trap | Codex | the scoping not taken: interference can only fail the check (OB3, measured), a leftover costs one requeue; the record no longer says "no race" |
| Bind both checks to the order's id and the worker's `PUT` | Codex | not taken: the check's trace id is its own, so no other order's spans can be in it, and OB3's mutants found no false pass |
| The tracing page cited order 53 in an output file that no longer holds it | Codex, OB3 | applied: cites R1.4's capture in reviews/115-tracing-page.md |
| A republish of an order from before R1.5 continues the request's trace, not a trace of its own | OB3 | applied to the page, with a test |
| The lost event's cause was stated more firmly than the cited evidence showed | Codex | applied with OB3's evidence, re-read by the orchestrator: Envoy logged the abandoned get (`"duration_ms":10010,"flags":"DC"`), MQ's web log dates the REST application's start, and MQ's counters show one put and one get more in that 10 s, each 430 bytes more, as the processed re-send at 01:00:45 left (`output/r1-5-lost-message.txt`, section 5) |

`tests/scripts/test_mq_trace_context.sh` gained the link, `error.type`, a non-numeric `attempt`, a
last attempt whose dead-letter put fails (`lost`), and the pre-R1.5 republish: 35 checks, 0
mismatches; on the reviewed head's code the worker stops on `ValueError` and orders-api's refusal
lacks `error.type`.

## The recorded run

`output/transcript.txt`, `scripts/run.sh --fresh` on R1.5's branch: 14 min 49 s, 92 checks, 0
failures (90 before R1.5, plus its two `phase6` checks); the gate made 66 reads, then parity 10 of
10. The two new checks:

- `otel: the worker's span joins the order's trace`: `server=1 first=1 first_ok=1 requeued=0
  later=0 later_ok=0 traces=1`;
- `otel: a requeued event's later attempt joins the trace`: `server=1 first=1 first_ok=0
  requeued=1 later=1 later_ok=1 traces=1`.

The order's trace grew from 12 spans to 22 across both services (`server=1 client=1 database=8
traces=1 spans=22`). The upgrade path (`scripts/run.sh` over the running lab) passed first, 5 min
42 s, with the same checks; it added the column to a database from before R1.5 (`traceparent text`,
on the 16 orders placed after the upgrade of 45).

The fresh run took 3 min 43 s longer than R1.4's 11 min 6 s, measured from the two transcripts'
step stamps:

| Step | R1.4 | R1.5 | Why |
|---|---|---|---|
| Parity | 3 min 12 s | 5 min 36 s | the requeue check moves the worker's requeue counter and Envoy's retries on `orders_api_internal` just before parity; they waited longest, 58 times each |
