**F1, the fix taken: OB1-lite's, not Codex's.** Codex proposed a second Envoy container on
`edge` publishing a Unix socket of the main Envoy's ops listener (a new service, a shared volume,
init and wait steps). OB1-lite measured how a connection from the Mac arrives: Podman's rootless
forwarder connects from Envoy's own address (`/proc/net/tcp` in Envoy: local and remote
`10.89.8.2`), a container from its own (`10.89.3.3`). Envoy's `source_type: SAME_IP_OR_LOOPBACK`
filter chain matches the first; every other source falls to a second chain with the old read-API
routes for VictoriaMetrics, and Grafana and Prometheus as before. One file, and it fails closed:
an engine whose forwarder connects from another address gives the Mac the read API only. Taken
for the smaller change with the same boundary.

Measured after Envoy restarted on it: the route test 45 ok, 0 mismatches (the four new
container refusals gave 4 mismatches before the restart); `tests/vmui_capture.py` 0 problems;
Grafana and Prometheus 200 from the Mac and Grafana 200 from a container. The route test now asks
the host route from the Mac itself.

**F2:** the alt text and the caption state the light picture's 10,689, and "histogram buckets".
Neither proposed test is committed: Codex's grep pins one wording; OB1-lite's OCR check runs on
macOS only. Both reproduced the defect, which is fixed in the text.
