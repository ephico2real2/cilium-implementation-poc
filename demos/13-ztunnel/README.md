# Demo 13 — ztunnel mTLS: the exercise, the proofs, and why it is not our standard (yet)

## Summary context

The question was "is Cilium mTLS enabled, and should it be our production standard?" The feature
Cilium *called* mutual authentication is deprecated in 1.20 and removed in 1.21
(`docs/summary/MTLS_EVALUATION.md`), so the only candidate is its named successor: **ztunnel**,
Istio's ambient-mode L4 proxy driven by Cilium as `encryption.type=ztunnel` — mTLS proper (per-
workload identity *and* encryption in one), beta in the 1.20.1 chart we run. This demo enables it
by the book, proves it on the wire, measures what it costs, and tests the two limitations its
documentation states against a real cluster. Every number is in `output/transcript.txt`, including
three failed attempts on poc1 that ended in an exact finding rather than a workaround.

**Verdict, in one paragraph.** ztunnel works and is provable — HBONE on port 15008, the request's
marker unreadable on the wire, a TLS handshake in the capture, per-namespace enrollment that flips
on and off with a label. It is also, today, **incompatible with ClusterMesh at the cluster-id
level**, **breaks every Cilium network policy on enrolled traffic (L4 and L7, measured)**, TCP-only,
beta, undocumented on the docs site, and costs **73 % of pod-to-pod throughput** on this rig. It is
not the production standard for this design. The standard stays: identity-based policy (Cilium
identities, L3–L7) plus **WireGuard** when encryption is required (demo 04, supported, half the
throughput cost). ztunnel is the feature to re-evaluate at GA, when it coexists with policy.

## Part 1 — three attempts on poc1, and the finding they produced

The docs say *"Cluster Mesh is not enabled"* is a precondition and *"attempting to enable both
will result in a validation error"*. The error is real — the agent will not start:

```
level=error msg="Invoke failed" error="ztunnel is not compatible with clustermesh" function="ztunnel.validateConfig (pkg/ztunnel/cell.go:40)"
level=fatal msg="unable to run agent: failed to start: failed to populate object graph: ztunnel is not compatible with clustermesh"
```

Three attempts to switch the mesh off far enough, each recorded:

| Attempt | What was switched off | Result |
|---|---|---|
| 1 | `cilium clustermesh disable` (the CLI) | same fatal — the CLI removed the apiserver but **left the mesh values in the helm release** (its own warnings said so) |
| 2 | helm: `clustermesh.useAPIServer=false`, `config.enabled=false`, `clusters=null` | same fatal — because the *restore* between attempts had run `cilium clustermesh enable`, which put `useAPIServer=true` back **and silently changed `tls.auto.method` from `certmanager` to `cronJob`** (gotcha #46) |
| 3 | the same, verified by rendering the chart: `clustermesh-config` absent from the ConfigMap | **same fatal** |

The source explains attempt 3 (`pkg/clustermesh/clustermesh.go:133`):

```go
if c.ClusterInfo.ID == 0 || c.ClusterMeshConfig == "" { return nil }
```

and the chart's DaemonSet sets `CILIUM_CLUSTERMESH_CONFIG=/var/lib/cilium/clustermesh/`
**unconditionally** (verified rendered and live). So `ClusterMeshConfig` is never empty on a helm
install, and the object is nil only when **`cluster.id == 0`**. poc1 is `cluster.id 1` — it must be,
for the mesh. **ztunnel cannot run on any cluster that has ever been given a cluster id**, connected
or not (gotcha #45). Changing a live cluster's id is not an option. poc1 was restored from its
pre-exercise values snapshot: agents 5/5, mesh apiserver re-issued by `clustermesh-root-ca`,
ClusterMesh 5/5 connected, Hubble OK, `scripts/check-routes.sh` 0 failures.

## Part 2 — the exercise on a throwaway cluster

`poc4` (`clusters/poc4.yaml`): 1 CP + 2 workers, its own docker network `kind-lab` `172.31.0.0/16`,
`cluster.id 0`, and ztunnel **at install time** as the docs describe
(`cilium/values-poc4-ztunnel.yaml`: KPR, `bpf.masquerade: true`, Hubble + relay,
`encryption.type: ztunnel`, `ca.type: internal` — Cilium's built-in CA, no SPIRE):

```bash
docker network create --subnet 172.31.0.0/16 --gateway 172.31.0.1 kind-lab
KIND_EXPERIMENTAL_DOCKER_NETWORK=kind-lab kind create cluster --config clusters/poc4.yaml
# the bootstrap + CA key pairs, generated by Cilium's own examples/kubernetes-ztunnel/generate-secrets.sh
kubectl -n kube-system create secret generic cilium-ztunnel-secrets --from-file=bootstrap-private.key --from-file=bootstrap-root.crt --from-file=ca-private.key --from-file=ca-root.crt
helm install cilium cilium/cilium --version 1.20.1 -n kube-system -f cilium/values-poc4-ztunnel.yaml
```

```
DS               DESIRED   READY
cilium           3         3
cilium-envoy     3         3          <- the service-mesh proxy, on every node
ztunnel-cilium   3         3
Encryption:              Ztunnel
```

Enrollment is per namespace and nothing else (the docs' only supported way):

```bash
kubectl label namespace forensic io.cilium/mtls-enabled=true
```
```
mtls-enrolled-namespaces: [{"Name": "forensic", "Status": {"kind": "Done"}}]
```

and it is implemented as **iptables inside each enrolled pod's network namespace** — the pod's own
traffic is redirected to the node's ztunnel on 15001 (out) / 15006 (in), HBONE on 15008 exempt:

```
*nat
-A CILIUM_OUTPUT ! -d 127.0.0.1/32 -p tcp -m mark ! --mark 0x539/0xfff -j REDIRECT --to-ports 15001
-A CILIUM_PREROUTING ! -d 127.0.0.1/32 -p tcp -m tcp ! --dport 15008 -m mark ! --mark 0x539/0xfff -j REDIRECT --to-ports 15006
```

Requests still work after enrollment (`client -> web: http 200`).

## Part 3 — proofs

**On the wire.** Capture on the backend node while the client sends three requests carrying
`X-Marker: PLAINTEXT-CANARY-7391`:

```
packets on port 15008 (HBONE): 82
marker readable in any packet: 0   (0 = the request was encrypted on the wire)
TLS handshake seen (ClientHello bytes 16 03 01): 1
00:21:18.866502 cilium_vxlan P   IP 10.0.2.60.51682 > 10.0.0.37.15008: Flags [P.] …
```

**What Hubble sees.** The enrolled pair talks on **15008**, identities intact — Hubble still
attributes the flow to `client` and `web`, but it is a TCP tunnel to it, not HTTP:

```
forensic/client:56766 (ID:8423) -> forensic/web-…:15008 (ID:51131) to-overlay FORWARDED (TCP Flags: ACK, PSH)
```

After disenrollment the same request is back on `:8080` and visible as before.

## Part 4 — the limitations the docs state, measured

**L4 policy** — `web-l4`: only `client` may reach `web` on 8080. Result with ztunnel on:

```
client (allowed by policy) -> web: http 000   (timeout)
fortio (NOT allowed)       -> web: i/o timeout
forensic/client:38010 <> forensic/web-…:15008  Policy denied DROPPED
```

The policy says 8080; the traffic arrives on 15008; **everything is dropped, the allowed peer
included**. Exactly the docs' sentence — *"L4 policies won't work except for directly targeting the
ztunnel HBONE port (15008)"* — and targeting 15008 cannot distinguish ports, so L4 policy is
effectively gone for enrolled namespaces.

**L7 policy (Cilium service mesh)** — `web-l7`: only `GET /` allowed. Expected 200 / 403 / 403:

```
GET /        -> http 000
GET /denied  -> http 000
PUT /        -> http 000
```

Envoy cannot see inside HBONE and the L4 match fails first; **Cilium's L7 service-mesh policy and
ztunnel are mutually exclusive on the same traffic.** This is the fact that ends the "standard"
question for us: the whole point of this PoC's demos 02, 05 and 09 is identity-aware L7 policy.

## Part 5 — what it costs (same cluster, same pods, enrollment toggled)

| | ztunnel ON (enrolled) | ztunnel OFF (disenrolled) |
|---|---|---|
| iperf3 pod-to-pod, median of 5 | **1,216 Mbit/s** (22 % spread) | **4,536 Mbit/s** (16 %) |
| churn (64 × `Connection: close`) pod-ip / clusterip / dns | 1,134 / 953 / 1,107 qps, p50 50–56 ms | 1,166 / 1,367 / 1,142 qps, p50 35–52 ms |

Throughput drops **73 %** — a userspace mTLS proxy on both ends. Churn on this 3-node cluster is
Hubble-bound in both states (demo 11 §3, cause 1), so it says little about ztunnel itself. VM load
was ~25 with three clusters running; the *ratio* is the finding, not the absolute numbers. For
comparison, WireGuard cost ~50 % on this rig in demo 04 (4,439 vs ~9,400 Mbit/s) and is GA.

## Part 6 — reproduce, and clean up

Everything is in `output/transcript.txt` in order, corrections included. The cluster was deleted

## What to take away

| Claim | Evidence |
|---|---|
| ztunnel gives real mTLS between enrolled pods | 82 HBONE packets, marker unreadable, TLS ClientHello in the capture |
| Enrollment is a namespace label, implemented as iptables inside the pod | `CILIUM_OUTPUT … REDIRECT --to-ports 15001`, `PREROUTING … 15006` |
| It cannot run on a cluster with a cluster id | `CILIUM_CLUSTERMESH_CONFIG` set unconditionally; nil only if `cluster.id == 0`; agent fatal on poc1 |
| It breaks Cilium network policy for enrolled traffic, L4 **and** L7 | allowed peer dropped (`Policy denied` on :15008); L7 policy 000/000/000 |
| It costs 73 % of throughput here | 1,216 vs 4,536 Mbit/s, same pods |
| Not the standard; WireGuard + identity policy is | GA, coexists with everything, ~50 % cost (demo 04) |
